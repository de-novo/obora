# 태스크 문서 작성 범위 규칙

## 목적
태스크(설계) 문서와 구현 코드의 경계를 명확히 정의하여, 설계 리뷰 시 구현 수준 디테일 요구로 인한 무한 루프를 방지한다.

## 핵심 원칙

> **"구현자가 방향을 잡을 수 있는 수준"이면 충분하다.**

설계 문서는 아키텍처 결정과 인터페이스 계약을 전달하는 것이 목적이다. 구현 세부사항은 코드와 코드 리뷰에서 다룬다.

## 회색 영역 의사결정 가이드

포함/제외가 모호한 경우 다음 기준으로 판단한다:

1. **외부 계약 여부**: 다른 모듈/시스템과의 약속이면 → 설계
2. **구현 비종속성**: 특정 구현(알고리즘, 데이터구조)을 가정하지 않는다면 → 설계
3. **SLA/제약 조건**: 성능 목표, 메모리 제한 등 측정 가능한 제약 → 설계
4. **기술 선택**: 특정 라이브러리, 캐시 전략 등 → 구현

### 경계 예시

| 항목 | 판정 | 이유 |
|------|------|------|
| "쿼리 응답 100ms 이내" | 설계 | SLA/외부 계약 |
| "Redis 캐시 사용" | 구현 | 특정 기술 선택 |
| "동시성 제어에 락 필요" | 설계 | 아키텍처 결정 |
| "ReentrantLock vs synchronized" | 구현 | 기술 선택 |
| "에러 복구 재시도 횟수 3회" | 설계 | 외부 동작 제약 |
| "재시도 간격 jitter 알고리즘" | 구현 | 내부 알고리즘 |

## 경계 논쟁 해결 프로세스

리뷰어와 작성자 간 "설계 범위 vs 구현 범위" 의견이 갈릴 때:

1. **1차**: 위 회색 영역 가이드 적용하여 합의 시도
2. **2차**: 합의 불가 시, 작성자가 해당 항목의 분류 근거를 1줄로 문서에 추가
3. **3차**: 그래도 합의 불가 시, **보수적 접근 원칙** 적용 — 의심스러우면 설계에 포함
4. **판정 주체**: 설계 문서의 assignee 또는 동일 도메인 엔지니어 기준으로 "구현 착수 가능 여부" 판단

## 포함/제외 기준

### ✅ 설계 문서에 포함

| 항목 | 설명 | 예시 |
|------|------|------|
| **WHY** | 왜 이 변경이 필요한가 | 비즈니스 목표, 기술 부채 해소 이유 |
| **WHAT** | 무엇을 변경하는가 | 변경 대상 파일/모듈 목록, 변경 범위 |
| **인터페이스 계약** | 타입, 시그니처, 에러코드 정의 | `interface AgentResolver { resolve(...): BaseAgent }` |
| **아키텍처 결정** | 패턴 선택과 그 이유 (ADR 수준) | "AbortSignal.any 사용 — timeout vs 외부 취소 분리 목적" |
| **실행 경로** | 주요 흐름 (happy path + error path) | 시퀀스 다이어그램, 흐름도 |
| **에러 모델** | 에러코드 정의 + 계층별 매핑 규칙 | E4001~E4014 정의표, 집계 규칙 |
| **DoD** | 완료 조건 (검증 가능한 수준) | "resolver bootstrap 실패 시 E4007 throw" |
| **파일별 변경 범위** | 어떤 파일에서 무엇이 바뀌는지 | 모듈 단위 변경 요약 |

### ❌ 설계 문서에서 제외 (구현/코드 리뷰 범위)

| 항목 | 이유 | 다루는 단계 |
|------|------|-----------|
| 테스트 케이스 상세 목록 | 구현 시 결정 | 코드 리뷰 |
| 로그 레벨, 메시지 포맷 | 운영 세부사항 | 코드 리뷰 |
| 내부 구현 알고리즘 세부 | 구현자 재량 | 코드 리뷰 |
| 에지케이스 전수 열거 | 무한 확장 위험 | 코드 리뷰 |
| 성능 최적화 디테일 | 구현 후 측정 기반 | 코드 리뷰 / 후속 태스크 |
| i18n, 로깅, 메트릭 세부 | 횡단 관심사 | 별도 태스크 또는 코드 리뷰 |
| 에러 메시지 문구 | 구현 시 결정 | 코드 리뷰 |
| E2E 테스트 환경 구성 | 인프라 범위 | 별도 태스크 |
| 클래스 내부 필드/메서드 구현체 | 구현 범위 | 코드 리뷰 |

## 코드 스니펫 규칙

1. **인터페이스 예시만 포함** — 타입 시그니처, 호출 패턴 수준
2. **구현체 코드는 최소화** — 패턴 설명 목적으로만, 복사-붙여넣기용 아님
3. **스니펫 길이 제한** — 하나의 스니펫은 20줄 이내 권장

## 에러코드 규칙

1. **코드 정의 + 발생 조건 + 처리 방침**까지 설계 문서 범위
2. **에러 메시지 문구, 국제화, 로그 포맷**은 구현 단계
3. **계층별 책임 매핑**은 설계 문서에 포함 (어디서 발생, 어디서 변환, 어디서 노출)

## 테스트 전략 규칙

1. **전략과 범위**는 설계 문서에 포함 — "단위/통합/E2E 중 어떤 수준이 필요한가"
2. **테스트 파일 목록**은 포함 가능 — 구현 가이드 역할
3. **개별 테스트 케이스 상세**는 제외 — 코드 리뷰에서 검증
4. **테스트 환경 구성**은 제외 — 인프라/별도 태스크

## 리뷰 기준 조정

### 설계 리뷰 (태스크 문서)
- **핵심 질문**: "이 문서로 구현을 착수할 수 있는가?"
- **평가 기준**: 아키텍처 정합성, 인터페이스 완결성, 실행 경로 명확성

### P0 상세 정의

설계 리뷰에서 P0는 다음 중 하나에 해당하는 경우에만 부여한다:

1. **구현 불가능** — 설계대로 구현했을 때 실행 자체가 불가능
2. **인터페이스 모순** — 타입/시그니처 계약이 자체 모순
3. **아키텍처 원칙 위반** — 프로젝트 핵심 원칙(에러 계층, single-writer 등) 위반
4. **방향 오류** — 어떤 구현을 하더라도 설계 결정 자체가 목표와 불일치

**P0가 아닌 것:**
- 구현 세부 미정의 → P2 (구현자 재량)
- 에지케이스 미열거 → P1 이하 (코드 리뷰)
- 테스트 케이스 미상세 → 범위 밖
- 로그/메트릭/i18n 누락 → 범위 밖

### 코드 리뷰 (구현)
- **핵심 질문**: "구현이 설계를 올바르게 반영했는가?"
- **평가 기준**: 코드 품질, 타입 안전성, 에러 처리, 테스트 커버리지
- **P0 기준**: 설계 위반, 런타임 크래시, 보안 취약점, 데이터 손실

## 문서 크기 가이드

| 태스크 규모 | 권장 문서 길이 | 참고 |
|-----------|-------------|------|
| Small (1-2 파일) | 50-100줄 | 인터페이스 변경 수준 |
| Medium (3-5 파일) | 100-200줄 | 모듈 간 연결 변경 |
| Large (6+ 파일) | 200-400줄 | 아키텍처 변경 |

**400줄 초과 시 태스크 분할을 고려한다.**

## 위반 사례와 올바른 예시

### ❌ 위반: 구현 디테일을 P0로 잡음
> "P0: RetryExhaustedError 클래스의 constructor 파라미터 순서가 미정의"
> "P0: 테스트 파일별 케이스 목록이 없음"
> "P0: 로그 레벨 정책이 미정의"

### ✅ 올바른 P0
> "P0: resolver bootstrap이 강제되지 않아 simulation fallback이 기본 경로로 동작"
> "P0: UserFacingErrorCode 타입에 실제 노출되는 코드가 누락되어 타입 시스템 모순"
> "P0: abort timeout과 외부 취소가 구분 불가능하여 에러 오분류"
