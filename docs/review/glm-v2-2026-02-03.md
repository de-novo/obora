## 상세 리뷰

### 잘 된 부분

1. **상세한 명세화**
   - 각 스펙 파일(8개)과 태스크(14개)가 매우 상세하게 작성됨
   - TypeScript 타입 정의, SQL 스키마, 알고리즘 의사 코드까지 포함
   - 구현자가 바로 시작할 수 있는 수준의 구체성

2. **모듈화 및 재사용성**
   - 공통 모듈(`@obora/core/graph`) 설계를 통해 순환 감지 로직 재사용
   - TASK-006(YAML 검증기)과 TASK-008(의존성 해석기)에서 순환 감지 공유
   - 코드 중복 방지를 위한 아키텍처 고려

3. **테스트 가능성**
   - 각 태스크에 구체적인 테스트 케이스 포함
   - 단위 테스트, 통합 테스트, 엣지 케이스 모두 고려
   - 테스트 가독성 높음 (expect 구문 사용 등)

4. **에러 처리 체계**
   - 에러 코드(Enum) 정의 및 에러 메시지 구조화
   - 라인 번호, 경로, 제안(suggestion) 포함
   - 사용자 친화적 에러 메시지 형식 제공

5. **MVP 범위 명확성**
   - 각 스펙 문서 끝에 MVP vs Full 구분 명시
   - MVP에서 구현되지 않는 기능 명확히 표기
   - 단계적 구현 계획 제시

6. **8원칙 설계 철학**
   - Fluid, Iterative, Easy 등 명확한 원칙 설정
   - 각 원칙이 실제 구현에 어떻게 적용되는지 구체적인 예시 제공

### 개선 필요

#### 1. 의존성 체인 복잡도

**문제점:**
- TASK-012(`obora run`)이 6개 태스크에 의존 (TASK-001, 002, 005, 006, 008, 010)
- 이론상 의존성이 적지만 실제 구현 시 복잡도 급증 가능
- `obora run`은 MVP의 핵심이면서도 가장 늦게 완료되어 통합 테스트가 어려움

**제안:**
- 의존성 인터페이스(Mock)를 통해 독립 테스트 가능하도록 설계
- TASK-012를 2개 이상의 서브 태스크로 분할 고려
- 인터페이스 기반 테스트 더블 패턴 도입

#### 2. 암묵적 의존성 추론의 구현 복잡도

**문제점:**
- `inputs/outputs` 파일 기반 의존성 추론은 구현 복잡도가 높음
- 파일 경로 매칭, 동적 의존성 그래프 업데이트 등 복잡한 로직 필요
- 에러 추적 및 디버깅이 어려움

**제안:**
- MVP에서는 `depends_on` 명시적 의존성만 사용
- 암묵적 의존성은 Full 버전으로 이연
- 단순성 우선 원칙 적용 (Easy 원칙)

```yaml
# MVP: 명시적 의존성만
steps:
  - name: design
    outputs: [design.md]
  - name: implement
    depends_on: [design]  # 명시적
```

#### 3. 동시성 제어 미정의

**문제점:**
- 락 파일(`locks/`)과 스냅샷(`snapshots/`) 폴더 구조 정의됨
- 하지만 MVP에서는 구현 제외되어 있음
- 동시 실행 시나리오(다른 터미널에서 `obora run` 실행)의 동작이 명확하지 않음

**제안:**
- MVP에서도 최소한의 락 파일 구현 권장 (단순 PID 파일 기반)
- 동시 실행 시 명확한 에러 메시지: `"Already running: lock file exists"`
- 락 파일 만료(expiration) 정책 정의 (예: 30분 이상 stale 시 자동 해제)

#### 4. DuckDB 마이그레이션 복잡도

**문제점:**
- 스키마 버전 관리(`schema_versions` 테이블) 정의됨
- 하지만 MVP에서는 마이그레이션 로직 구현이 제외됨
- 추후 스키마 변경 시 하위 호환성 이슈 발생 가능

**제안:**
- MVP에서는 초기 스키마 생성만 사용 (CREATE TABLE IF NOT EXISTS)
- Full 버전에서 마이그레이션 로직 구현
- MVP 범위에서는 스키마 변경 불가 명시

#### 5. OpenClaw 연동 로직 불명확

**문제점:**
- `sessions_spawn` 호출 형식은 정의됨

- AI 에이전트가 시간 초과/실패 시 어떻게 복구할지 명확하지 않음

**제안:**

### 3. OpenClaw 연동 래퍼 클래스 정의

**이유:** 타임아웃, 재시도, 에러 처리 표준화

**구현 내용:**
```typescript
// packages/core/src/agent-executor.ts
export class AgentExecutor {
  async execute(
    agent: AgentDefinition,
    inputs: Map<string, string>
  ): Promise<string> {
    const maxRetries = agent.config?.retry ?? 0;
    const retryDelay = this.parseDuration(agent.config?.retry_delay ?? '30s');

    for (let attempt = 0; attempt <= maxRetries; attempt++) {
      try {
        return await this.callOpenClaw(agent, inputs);
      } catch (error) {
        if (attempt === maxRetries) {
          throw new AgentExecutionError(agent.id, error);
        }
        await this.sleep(retryDelay * Math.pow(2, attempt)); // 지수 백오프
      }
    }
    throw new Error('Unreachable');
  }

  private async callOpenClaw(
    agent: AgentDefinition,
    inputs: Map<string, string>
  ): Promise<string> {
    const prompt = this.buildPrompt(agent, inputs);
    return await openclaw.spawn({
      task: prompt,
      model: agent.config?.model ?? 'zai/glm-4.7',
      timeout: agent.config?.timeout ?? 300000,
      cleanup: 'delete'
    });
  }

  private parseDuration(duration: string): number {
    const match = duration.match(/^(\d+)([smhd])$/);
    if (!match) return 30000;
    const [, value, unit] = match;
    const unitToMs = { s: 1000, m: 60000, h: 3600000, d: 86400000 };
    return parseInt(value) * unitToMs[unit];
  }
}
```

## 결론

obora-kit v3 스펙/태스크 문서는 전반적으로 매우 상세하고 잘 작성되어 있습니다. 구현자가 바로 시작할 수 있는 수준의 구체성을 갖추고 있으며, 테스트 케이스와 타입 정의가 포함되어 있습니다.

**주요 강점:**
- 상세한 명세화와 타입 정의
- 모듈화 및 재사용성 고려
- 테스트 가능성 확보
- 명확한 MVP 범위 정의

**개선이 필요한 영역:**
- 암묵적 의존성의 구현 복잡도
- 동시성 제어/에러 복구 로직
