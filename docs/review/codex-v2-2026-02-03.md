# Codex Review Result

## Summary
- Rating: 중
- Score: 6/10

## Detailed Review
### Strengths
- Spec and tasks are aligned on MVP scope and command set; the end-to-end flow (init → new → plan → run → done) is consistently described across docs/spec/01-overview.md and docs/spec/02-cli-commands.md.
- Workflow YAML schema is well structured with clear defaults and examples, aiding type definition and parser implementation (docs/spec/03-workflow-yaml.md).
- Task breakdown is practical and incremental, with test case hints for each task (docs/tasks/P0-MVP/TASK-001-project-setup.md, docs/tasks/P0-MVP/TASK-002-cli-scaffold.md).

### Areas for Improvement
- Inconsistent CLI options between spec and tasks: `obora init` uses `--workflow` in spec but task defines `--template`; `obora new` uses `--workflow`/`--from-existing` in spec but task defines `--type`/`--description`. This will cause API design drift and implementation ambiguity (docs/spec/02-cli-commands.md, docs/tasks/P0-MVP/TASK-003-obora-init.md, docs/tasks/P0-MVP/TASK-004-obora-new.md).
- Workflow YAML schema includes `backoff` in examples but not in the formal schema/types, creating a correctness gap for type definitions and validation (docs/spec/03-workflow-yaml.md).
- `action` type is described as a list of maps with different keys, but no canonical TypeScript discriminated union or JSON Schema mapping is specified; this increases implementation complexity and validation risk (docs/spec/03-workflow-yaml.md).
- The parser task mentions `Dependency` interface, but the spec defines dependency semantics via `depends_on` and implicit inputs/outputs; the expected shape of computed dependencies and whether they are persisted is not defined (docs/spec/03-workflow-yaml.md, docs/tasks/P0-MVP/TASK-005-yaml-parser.md).
- Status tracking file (`status.yaml`) is introduced in TASK-004, but no schema is defined in the reviewed specs; this creates type and validation gaps and uncertain API surface (docs/tasks/P0-MVP/TASK-004-obora-new.md).

### Missing Items
- Explicit TypeScript types for `duration`, `action`, `on_failure`, `env`, and `config` defaults, including parsing rules and error messages (docs/spec/03-workflow-yaml.md).
- CLI exit code map consistency for all commands implemented in tasks; tasks don’t specify expected exit codes, while spec does for some commands (docs/spec/02-cli-commands.md, docs/tasks/P0-MVP/TASK-00x*.md).
- YAML parser test fixtures and validation boundaries (e.g., unknown fields, duplicate step names, invalid duration format) are not defined (docs/tasks/P0-MVP/TASK-005-yaml-parser.md).
- Definition of feature name validation rules (allowed charset, max length, reserved names) is referenced but not specified, creating inconsistent behavior across commands (docs/spec/02-cli-commands.md, docs/tasks/P0-MVP/TASK-004-obora-new.md).
- Workflow file resolution rules (path resolution relative to `.obora/`, project root, or explicit path) are implied but not formalized, risking inconsistent CLI behavior (docs/spec/02-cli-commands.md, docs/spec/03-workflow-yaml.md).

## Top 5 Priority Fixes
1. Unify CLI option contracts across spec and tasks (init/new) and lock them in a single source of truth to prevent implementation drift.
2. Define full Workflow YAML type system (including `backoff`, `action`, `duration`) with precise parsing/validation rules.
3. Specify dependency graph computation outputs (implicit vs explicit edges) and the expected `Dependency` type shape for parser output.
4. Add `status.yaml` schema and lifecycle transitions to avoid ambiguous state tracking.
5. Expand parser test strategy to include invalid duration formats, duplicate step names, unknown fields, and implicit dependency detection.
