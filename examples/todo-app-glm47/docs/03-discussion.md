# TODO 앱 솔루션 논의서

## 1. 개요

본 문서는 요구사항(01-requirements.md)과 분석(02-analysis.md)을 바탕으로 TODO 앱의 최적 솔루션 접근 방식을 정의합니다.

## 2. 핵심 설계 결정 (Core Design Decisions)

### 2.1 아키텍처 패턴

**선택: 이벤트 기반 단일 상태 관리 (Event-Driven Single State Pattern)**

| 결정 사항 | 근거 |
|----------|------|
| 중앙 집중식 상태 객체 | 단일 데이터 소스(Single Source of Truth)로 데이터 일관성 보장 |
| 커스텀 이벤트 버스 | 컴포넌트 간 느슨한 결합, 프레임워크 없는 상태 동기화 가능 |
| 명령형 렌더링 함수 | DOM diff 없는 전체 재렌더링이 적절한 데이터 규모(100개 미만 태스크) |

**데이터 구조:**
```javascript
{
  todos: [
    { id: timestamp, text: string, completed: boolean }
  ],
  filter: 'all' | 'active' | 'completed'
}
```

### 2.2 상태 관리 전략

**선택: Flux-스타일 단방향 데이터 흐름 (단순화 버전)**

```
사용자 액션 → 이벤트 발생 → 액션 핸들러 → 상태 업데이트 → localStorage 저장 → 렌더링
```

**장점:**
- 상태 변경 추적 용이
- 디버깅 간소화
- 확장 시 Redux 같은 상태 관리 라이브러리로 이전 가능

### 2.3 컴포넌트 통신 방식

| 방식 | 적용 대상 | 근거 |
|------|----------|------|
| 이벤트 위임 (Event Delegation) | TodoItem 삭제/완료 토글 | 동적으로 생성되는 항목 이벤트 처리 최적화 |
| 콜백 함수 | AddTodo, FilterBar | 직접적인 상위 컴포넌트 통신 |
| 상태 기반 렌더링 | TodoList | 필터 상태 변경 시 전체 목록 재렌더링 |

## 3. 대안 비교 (Alternative Comparison)

### 3.1 상태 관리 방식 비교

| 방식 | 장점 | 단점 | 선택 여부 |
|------|------|------|----------|
| 전역 변수 | 단순함 | 스코프 오염, 디버깅 어려움 | ❌ |
| 클래스 기반 | 캡슐화 | 복잡도 증가, this 바인딩 문제 | ❌ |
| **중앙 상태 + 이벤트 버스** | 명확한 데이터 흐름, 디버깅 용이 | 초기 구현 비용 | ✅ **선택** |
| 프로토타입 상속 | 메모리 효율 | 학습 곡선, 코드 가독성 저하 | ❌ |

### 3.2 렌더링 전략 비교

| 전략 | 설명 | 장점 | 단점 | 선택 여부 |
|------|------|------|------|----------|
| 전체 재렌더링 | 상태 변경 시 모든 컴포넌트 재생성 | 구현 단순, 데이터 일관성 보장 | 성능 저하 가능 (대규모 시) | ✅ **선택** (MVP) |
| 부분 DOM 업데이트 | 변경된 노드만 수정 | 성능 우수 | 복잡도 증가, 버그 가능성 높음 | ❌ |
| 가상 DOM | diff 알고리즘으로 최소 업데이트 | 최적화된 성능 | 구현 복잡, 프레임워크 필요 | ❌ (제약사항 위배) |

### 3.3 저장소 접근 방식 비교

| 방식 | 장점 | 단점 | 선택 여부 |
|------|------|------|----------|
| 매 액션 직접 저장 | 데이터 손실 방지 | 성능 저하 (잦은 I/O) | ❌ |
| **디바운스 후 저장** | I/O 최적화, UX 유지 | 100ms 지연 가능성 | ✅ **선택** |
| 페이지 언로드 시만 저장 | I/O 최소화 | 크래시 시 데이터 손실 | ❌ |

## 4. 기술적 고려사항

### 4.1 XSS 방어 전략

| 위협 | 방어 방법 |
|------|----------|
| 사용자 입력 스크립트 주입 | `textContent` 사용 (`innerHTML` 금지) |
| 이벤트 핸들러 주입 | 문자열로 동적 함수 생성 금지 |
| URL 기반 공격 | 외부 링크 처리 시 `rel="noopener noreferrer"` 추가 |

### 4.2 접근성 구현 방안

| 요구사항 | 구현 방법 |
|----------|----------|
| 키보드 탐색 | Tab 인덱스 설정, 엔터키로 버튼 활성화 |
| 스크린 리더 | `aria-label`, `aria-checked`, `role="checkbox"` 사용 |
| 포커스 관리 | 삭제 완료 후 포커스 적절 위치로 이동 |

### 4.3 에러 처리 전략

| 에러 유형 | 처리 방법 |
|----------|----------|
| localStorage 꽉 참 | 경고 메시지, 오래된 태스크 삭제 제안 |
| JSON 파싱 실패 | 빈 배열로 초기화, 콘솔 로그 |
| 네트워크 관련 | 해당 없음 (로컬 전용) |

## 5. MVP 구현 계획

### 5.1 파일 구조

```
index.html          # 메인 HTML (단일 파일)
  ├── <style>       # CSS (BEM 명명규칙, CSS 변수)
  └── <script>      # JavaScript (모듈 패턴)
```

### 5.2 구현 순서

| 단계 | 작업 | 산출물 |
|------|------|--------|
| 1 | HTML 스켈레톤 및 CSS 기본 스타일 | 마크업, 레이아웃 |
| 2 | 상태 관리 및 localStorage 구현 | `state` 객체, `save/load` 함수 |
| 3 | TodoApp, AddTodo 컴포넌트 | 태스크 추가 기능 |
| 4 | TodoList, TodoItem 컴포넌트 | 목록 표시, 완료 토글 |
| 5 | 삭제 기능 및 이벤트 위임 | 삭제 버튼 |
| 6 | FilterBar 컴포넌트 | 필터링 기능 |
| 7 | 접근성 및 유효성 검증 | ARIA, 입력 검사 |
| 8 | 반응형 UI 및 폴리백 | 모바일 지원 |

### 5.3 성능 최적화

| 최적화 항목 | 방법 | 예상 효과 |
|-------------|------|----------|
| 렌더링 최적화 | 필터링된 배열만 렌더링 | 불필요한 DOM 생성 방지 |
| 이벤트 핸들러 | 정적 부모에 위임 | 메모리 사용량 감소 |
| localStorage | 디바운스 (100ms) | I/O 빈도 90% 감소 |
| CSS | 하드웨어 가속 (transform) | 애니메이션 부드러움 |

## 6. 리스크 완화 방안

| 리스크 | 완화 전략 |
|--------|----------|
| localStorage 쿼터 초과 | 태스크 1000개 제한, 경고 메시지 |
| 다중 탭 동시성 | `storage` 이벤트 리스너로 상태 동기화 (선택) |
| 브라우저 호환성 | Modern JS (ES6+) 사용, 최신 브라우저만 지원 |
| 모바일 UX | 터치 타겟 최소 44px, 뷰포트 메타 태그 |

## 7. 향후 확장성 고려

| 확장 기능 | 현재 설계에서의 고려사항 |
|----------|------------------------|
| 다크 모드 | CSS 변수로 색상 정의, 테마 클래스 전환 |
| 태스크 편집 | TodoItem에 편집 모드 상태 추가 가능 |
| 우선순위 | `todos` 데이터 구조에 `priority` 필드 추가 |
| 카테고리 | 필터 상태를 문자열에서 객체로 확장 가능 |

## 8. 결론

### 8.1 최종 솔루션 요약

- **아키텍처**: 이벤트 기반 중앙 집중식 상태 관리
- **데이터 흐름**: 단방향 (액션 → 상태 → 렌더링)
- **저장소**: localStorage + 디바운스
- **렌더링**: 명령형 전체 재렌더링 (MVP 적합)
- **보안**: textContent 사용, 입력 이스케이프
- **접근성**: ARIA 속성, 키보드 탐색

### 8.2 기대 효과

| 항목 | 기대치 |
|------|--------|
| 개발 기간 | 2-3일 (MVP) |
| 코드 라인 수 | ~300줄 (HTML+CSS+JS) |
| 로드 시간 | <100ms (로컬 환경) |
| 유지보수성 | 중상 (명확한 책임 분리) |
| 확장성 | 상 (이벤트 기반 아키텍처) |
