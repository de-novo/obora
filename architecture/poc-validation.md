# PoC 검증 현황 — 자동화 루프 → obora-kit 매핑

> 일시: 2026-02-10
> 배경: 현재 자동화 리뷰 루프(bash 스크립트)는 obora-kit의 PoC이다.
> PoC에서 실증된 교훈이 곧 obora-kit의 제품 요구사항이 된다.

## 2. PoC에서 검증된 핵심 원칙

### 2.1 체크리스트 기반 수렴 → 결정적 검증

- **문제**: "이 코드 리뷰해줘" → 비결정적 (매번 다른 관점)
- **해결**: "30개 항목 YES/NO" → 결정적 (수렴)
- **실증**: TASK-025, 027에서 10/10 만점 달성
- **제품 적용**: Verifier 에이전트의 핵심 동작 패턴

### 2.2 다중 모델 합의 → 맹점 보완

- **문제**: 단일 모델은 주의(Attention) 편향으로 일부 이슈를 놓침
- **해결**: 4개 모델 병렬 리뷰 + 불일치 항목 토론
- **실증**: TASK-025 Loop 1에서 단일 모델은 8개 이슈 중 최대 5개만 발견
- **제품 적용**: Actor 시스템의 다중 에이전트 병렬 실행

### 2.3 Per-issue fix + rollback → 안정적 자동 수정

- **문제**: 통짜 수정(legacy fixer)은 비결정적 → 점수 하락
- **해결**: 이슈별 개별 수정 → 테스트 → 실패 시 롤백
- **실증**: 12/12 이슈 수정 성공, 0 롤백 (TASK-025)
- **제품 적용**: Supervision 패턴 (재시작 전략, 백오프)

### 2.4 발산→수렴 패턴

- **원칙**: LLM을 발산적 사고에 1회 사용 → 수렴적 검증에 반복 사용
- **실증**: 8→9 벽 돌파의 결정적 요인
- **제품 적용**: `obora plan`(발산) → `obora run`(수렴)

## 3. 아직 검증 필요한 항목

### 3.1 심판 제거 → 전원 합의 토론 (v2)

- **현재**: Opus 심판이 최종 판정 (SPOF 위험)
- **목표**: 모든 모델이 토론으로 합의할 때까지 반복
- **제품 적용**: Board 시스템 v2 (투표→토론 전환)
- **상태**: 미검증

### 3.2 L0 자동 질문 (요구사항 정제)

- **현재**: 인간이 스펙 직접 작성
- **목표**: AI가 질문 → 인간이 답 → 포멀한 스펙 자동 도출
- **제품 적용**: `obora plan` 대화형 모드
- **상태**: 토론에서 개념 정립, 미구현

### 3.3 Freeze Gate (수정 금지 영역)

- **현재**: 매 루프마다 모든 파일이 수정 대상
- **목표**: 2회 연속 통과 파일은 수정 금지 → 진동 방지
- **제품 적용**: 워크플로우 게이트 시스템
- **상태**: 설계 완료, 미구현

### 3.4 스펙 문서 SSOT 자동 동기화

- **현재**: 코드 변경 후 스펙 수동 갱신
- **목표**: 코드 변경 시 스펙 자동 검증 + 갱신 알림
- **상태**: 미검증

## 7. 셀프 호스팅 — 컴파일러 비유

### 7.1 obora-kit = 자연어 컴파일러

> **"자연어 요구사항을 검증된 코드로 컴파일하는 도구"**

| 컴파일러 단계                     | obora-kit 단계                                 |
| --------------------------------- | ---------------------------------------------- |
| **Lexing** (토큰화)               | L0: 요구사항을 개별 명제로 분해                |
| **Parsing** (구문 분석)           | L1: 명제를 스펙/체크리스트로 구조화            |
| **Semantic Analysis** (의미 분석) | L1: 체크리스트 간 일관성 검증 (다중 모델 합의) |
| **Optimization**                  | L2: per-issue fix + rollback (최적화)          |
| **Code Generation**               | L2: 검증된 코드 산출                           |
| **Linking**                       | 패키지 통합, 테스트 통과                       |

### 7.2 셀프 호스팅 경로

컴파일러는 보통 다른 언어로 구현되다가, 언어의 수준이 올라가면 자기 자신의 컴파일러를 만든다:

```
C 컴파일러:    어셈블리로 작성 → C로 C 컴파일러 작성
Go:           C로 작성 → Go 1.5부터 Go로 Go 컴파일러
Rust:         OCaml로 작성 → Rust로 Rust 컴파일러
obora-kit:    bash 스크립트(PoC)로 검증 → obora-kit으로 obora-kit 개발
```

### 7.3 부트스트래핑 단계

| 단계    | 도구                      | 대상                       | 상태       |
| ------- | ------------------------- | -------------------------- | ---------- |
| Stage 0 | bash 스크립트 (PoC)       | obora-kit 핵심 모듈 개발   | 🔄 진행 중 |
| Stage 1 | obora-kit CLI (최소 기능) | obora-kit 나머지 모듈 개발 | ⏳ 대기    |
| Stage 2 | obora-kit (완전체)        | obora-kit 자체 유지보수    | ⏳ 대기    |

### 7.4 셀프 호스팅 마일스톤

**셀프 호스팅 달성 = 제품 성숙도의 증명**

- 컴파일러가 자기 자신을 컴파일할 수 있으면 → "이 언어는 실제 프로젝트를 만들 수 있다"
- obora-kit이 obora-kit 자체를 개발할 수 있으면 → "이 도구는 실제 프로젝트에 쓸 수 있다"

**v1 출시 기준점: `obora run`으로 obora-kit 태스크를 돌리는 날 = 셀프 호스팅 달성일**

### 7.5 필요 조건

셀프 호스팅 달성을 위해 필요한 최소 기능:

1. **Actor 시스템** — 다중 에이전트 병렬 실행 ✅ (TASK-024~028 완료)
2. **Board 시스템** — 다중 모델 합의 (투표 v1) ⏳
3. **Workflow Engine** — `obora run` 파이프라인 실행 ⏳
4. **CLI** — `obora init`, `obora quickstart`, `obora run` ✅ (P0 완료)
5. **Artifact Context** — 단계 간 파일 전달 ⏳
