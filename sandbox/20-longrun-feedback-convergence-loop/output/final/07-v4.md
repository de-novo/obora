# Objective

Define a reproducible feedback-convergence workflow for Obora canonical sandbox step 20, where a single task is drafted, evaluated, revised, and re-evaluated through multiple iterations within a controlled sandbox environment.

# Constraints

- All outputs must remain sandbox-local under `/Users/denovo/workspace/github/obora-kit/sandbox/20-longrun-feedback-convergence-loop/`.
- The runner operates under the long-running contract with a watchdog and a large safety ceiling to permit multiple iterations without premature termination.
- No external services or non-sandbox paths may be referenced or modified.
- Scores must improve monotonically across evaluations (each evaluation score must be greater than or equal to the previous score).
- The convergence loop stops only when the final score reaches at least 9/10.
- Every revision after v1 must read and apply the immediately previous evaluation feedback as a standing workflow invariant.

# Proposed Approach

- Feedback applied from 06-eval-v3: Added verification invariants for logs, workflow result JSON, and regenerated artifacts (C9), and extended Reuse Notes to cover adapting the pattern to other structured checklist tasks (C10).
1. Initialize the sandbox workspace with required inputs (brief.md, rubric.md).
2. Execute a feedback-convergence loop comprising exactly:
   - Four candidate versions (v1, v2, v3, v4)
   - Four corresponding evaluations (e1, e2, e3, e4)
3. Each iteration:
   - Read the previous evaluation (if any) and apply feedback to produce the next candidate.
   - Run rubric-based scoring on the current candidate.
4. Continue until all four candidate/evaluation cycles complete, then archive the final artifacts.
5. Upon completion, produce an archive note with the following required headings:
   - **Summary of Convergence**: Brief description of the feedback loop outcome.
   - **Score Trajectory**: List of scores from e1 through e4 demonstrating monotonic improvement.
   - **Reuse Notes**: Guidance for adapting this feedback-convergence pattern to other structured checklist tasks, including how to substitute rubrics, adjust iteration counts, and calibrate score thresholds for different domains.
6. Verification invariants (required for reproducibility):
   - Logs: All iteration logs must be present under the sandbox output directory, showing each candidate generation and evaluation step.
   - Workflow result JSON: A final workflow-result.json must exist with score history, iteration count, and convergence status.
   - Fresh-run reproducibility: On a clean sandbox, re-running the same workflow must regenerate identical final artifacts (candidates, evaluations, archive note) up to non-semantic timestamp differences.

# Risks

- **Timeout risk**: Even with a large safety ceiling, excessive iteration complexity could approach limits.
- **Feedback loop stall**: If feedback does not produce actionable changes, subsequent candidates may not differ meaningfully.
- **Rubric drift**: Ensure the rubric is applied consistently across all four evaluations to maintain comparability.
